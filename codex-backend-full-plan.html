نقطة المتابعة الأحدث — 2026-09-07:
- المرحلة 5 قيد التنفيذ، وليست مكتملة بكل بنودها الموسعة أدناه.
- أنجز البحث وpagination للعملاء والموردين في Backend وربط البحث والمسح بواجهات Angular.
- أضيف الرقم الضريبي للنموذجين، وتعديل وحذف المنتجات في Angular دون إعادة إرسال كمية افتتاحية عند التعديل.
- نجح سابقًا فحص CRUD على عميل ومورد ومنتج خدمة تجريبيين عبر قاعدة النظام الحالية؛ أزيلت السجلات التجريبية من القوائم بالحذف المنطقي مع بقاء التدقيق.
- أنجز اليوم فلتر customer_id وdue_only وحجم صفحة آمن لقائمة الفواتير، وربط سجل العميل واختيار فواتيره المستحقة بهما بدل تصفية صفحة عامة محليًا.
- نجح فحص تجميع Angular بدون إخراج ملفات، وتنسيق ملفات PHP المعدلة.
- تعذر فحص API لفلاتر الفواتير الجديدة لأن السيرفر على 127.0.0.1:8000 غير متاح وقت المحاولة. لا تعتبر هذا الفحص ناجحًا.
- المتابعة: تشغيل الباك وفحص الفلاتر الجديدة؛ ثم استكمال مطابقة البنود المتبقية للمرحلة 5، خاصة كشف حساب العميل وواجهات ربط منتجات المورد والقيود المرجعية. لا تنتقل للمرحلة 6 بوصف المرحلة 5 مكتملة قبل ذلك.
- تعليمات الاختبار: المستخدم سمح بالفحص على قاعدة النظام نفسها. لا تستخدم قاعدة منفصلة ولا RefreshDatabase أو migrate:fresh على قاعدة النظام؛ عمليات الكتابة للاختبار على سجلات تجريبية واضحة فقط دون المساس بالفواتير والأرصدة الحقيقية.
- لا تُعد الفحوص السابقة لمجرد التكرار، وقراءة صور فواتير المورد بالذكاء الاصطناعي ما زالت مؤجلة.

المطلوب:
نفّذ الخطة الكاملة التالية لتطوير وتحسين Backend النظام من المرحلة 0 حتى المرحلة 9. لا تكتفِ بالتخطيط أو المراجعة؛ افحص الموجود أولًا، ثم أكمل النواقص فعليًا واختبر كل مرحلة. اعتبر جميع المراحل مطلوبة، بما فيها الاستيراد والذكاء الاصطناعي، لكن لا تعِد كتابة ميزة صحيحة ومكتملة لمجرد أنها موجودة مسبقًا.

قواعد البداية الإلزامية:
1. افحص الكود والحالة الفعلية للمشروع قبل أي تعديل، ولا تعتمد على وصف قديم أو تخمين.
2. اقرأ backend/AGENTS.md وكل skills وقواعد .ai/rules المطابقة للملفات التي ستعدلها والتزم بها.
3. افحص git status والتغييرات الموجودة مسبقًا. تغييرات المستخدم ملكه؛ لا تحذفها ولا ترجعها ولا تستبدلها.
4. التزم ببنية Laravel الحالية: API versioning، Form Requests، API Resources، Services للعمليات متعددة الخطوات، UUIDs، Transactions، AuditLogService، والصلاحيات الحالية.
5. استخدم Laravel Sanctum وآلية permissions الموجودة. دور Admin يجب أن يبقى بصلاحيات مطلقة.
6. لا تستخدم بيانات ثابتة أو IDs مكتوبة يدويًا، ولا تستخدم بيانات وهمية بدل الـAPI الحقيقي.
7. لا تشغّل migrate:fresh أو أي أمر يمسح قاعدة المستخدم. استخدم قاعدة اختبار معزولة للاختبارات.
8. لا تضف dependency إلا إذا كانت ضرورية، وبعد فحص النسخة والتوافق والحصول على الموافقة عند الحاجة.
9. لا تعدّل الاختبارات فقط لجعلها تمر؛ أصلح السبب الحقيقي.
10. نفّذ العمل على دفعات صغيرة مترابطة. بعد كل مرحلة شغّل الاختبارات المحددة لها وسجّل النتيجة.
11. لا تتوقف بعد مرحلة واحدة ما دام يمكن متابعة العمل بأمان. إذا ظهر مانع حقيقي، وثّقه بدقة وتابع ما لا يعتمد عليه.
12. التركيز الأساسي Backend. عدّل Frontend فقط عندما يكون ذلك ضروريًا لإتاحة ميزة Backend مكتملة للمستخدم، مع الحفاظ على Angular وngx-admin/Nebular والـRTL.

المرحلة 0: Swagger / OpenAPI
الحالة السابقة: موجود إلى حد كبير، ويجب تدقيقه لا افتراض اكتماله.

المطلوب:
- جرد جميع مسارات /v1 الفعلية ومقارنتها بتوثيق OpenAPI.
- توثيق الطلبات والاستجابات، pagination، validation errors، 401، 403، 404، 409 و422.
- توثيق Sanctum Bearer authentication لجميع المسارات المحمية.
- التأكد أن Swagger محمي أو معطّل بطريقة آمنة في Production حسب إعدادات المشروع.
- منع تسريب أسرار أو أمثلة حقيقية حساسة في التوثيق.
- إصلاح اختبار OpenApiDocumentationTest وأي اختلاف حقيقي بين المسارات والتوثيق.

معيار الإنجاز:
- كل endpoint تشغيلي تحت /v1 موثق وقابل للمطابقة مع route:list.
- اختبارات OpenAPI تمر.

المرحلة 1: المخزون والجرد

راجع وأكمل:
- أرصدة المنتج حسب المستودع مع available وreserved وreorder level.
- سجل حركات المخزون مع الفلاتر وpagination والعلاقات الصحيحة.
- تقرير المخزون المنخفض.
- التسوية مع سبب واضح ومنع الكميات غير المنطقية.
- تسجيل التالف مع السبب والمستخدم.
- التحويل بين مستودعين ضمن transaction واحدة وقفل الصفوف اللازمة ومنع التحويل لنفس المستودع أو كمية غير متاحة.
- دورة الجرد: إنشاء، إدخال الكميات، مراجعة، اعتماد/تطبيق، إلغاء، وحركات الفروقات.
- منع تعديل الجرد بعد تطبيقه أو إلغائه.
- ضمان idempotency أو منع الضغط المكرر في العمليات الحساسة.
- تسجيل Audit Log لكل mutation.

اختبارات القبول:
- تسوية زيادة ونقصان.
- تالف.
- تحويل ناجح وفاشل بسبب نقص الكمية.
- جرد كامل بحالاته وفروق المخزون.
- تحقق من الأرصدة والحركات بعد كل عملية.

المرحلة 2: المشتريات وحساب المورد

راجع وأكمل:
- CRUD أوامر الشراء ضمن الحالات المسموحة.
- إنشاء أمر ببنود متعددة وحساب subtotal/tax/discount/total بدقة decimal.
- إرسال الأمر وإلغاؤه بقواعد حالات واضحة.
- استلام جزئي واستلام كامل، ومنع استلام كمية أكبر من المتبقي.
- إنشاء Goods Receipts وربطها بالأمر والمستخدم والمستودع.
- زيادة المخزون مرة واحدة فقط لكل استلام.
- تحديث حالة أمر الشراء تلقائيًا.
- إنشاء قيد حساب المورد عند الاستلام وفق سياسة النظام.
- دفعة المورد وربطها اختياريًا بأمر شراء، مع طريقة الدفع والمرجع والملاحظات والرصيد قبل/بعد.
- كشف حساب المورد وسجل دفعاته مع الفلاتر وpagination.
- استخدام row locking وtransactions حيث يلزم لمنع الاستلام أو الدفع المكرر.
- Audit logs كاملة.

اختبارات القبول:
- إنشاء وإرسال وإلغاء ضمن الحالات الصحيحة والخاطئة.
- استلام جزئي ثم كامل.
- فشل الاستلام الزائد أو المكرر.
- تحقق من زيادة المخزون وحساب المورد والرصيد.
- تسجيل دفعة والتحقق من القيد والرصيد.

المرحلة 3: الفواتير والمرتجعات

راجع وأكمل:
- قائمة الفواتير وتفاصيل الفاتورة مع البنود والضرائب والخصومات والمدفوعات والعميل والشفت.
- حالات order وpayment status وتناسقها بعد الدفع أو البيع الآجل أو المرتجع.
- الإرجاع الجزئي والكامل مع منع تجاوز الكمية القابلة للإرجاع.
- إعادة المخزون للمنتجات المخزنية فقط.
- Refund آمن مرتبط بالمرتجع وطريقة الدفع.
- تحديث الإجماليات وصافي المبيعات والربح وحساب العميل بصورة صحيحة بعد المرتجع.
- منع تكرار refund أو المرتجع ذاته.
- Audit logs واختبارات حالات الحواف.
- لا تنفّذ طباعة Blade أو قوالب ورقية إلا إذا طلبها المستخدم صراحة في الجلسة؛ أبقِ بيانات الفاتورة API-ready للطباعة.

اختبارات القبول:
- بيع نقدي، متعدد طرق الدفع إن كان مدعومًا، وآجل.
- مرتجع جزئي ثم كامل.
- فشل إرجاع كمية زائدة.
- Refund والتحقق من المخزون والأرصدة والتقارير.

المرحلة 4: سجل التدقيق والصلاحيات

المطلوب:
- إنشاء API محمي لعرض audit_logs مع pagination.
- فلاتر حسب المستخدم، action، subject type، subject id، والفترة الزمنية.
- Resource آمن لا يعرض كلمات مرور أو tokens أو أسرار أو بيانات حساسة.
- التأكد أن كل create/update/delete والعمليات التجارية المهمة مسجلة، وأن العرض التفصيلي فقط يسجل viewed عند سياسة المشروع.
- مراجعة مصفوفة الصلاحيات لكل endpoints ومنع المسارات غير المحمية بالخطأ.
- Admin bypass كامل ومتناسق في Backend وFrontend.
- إضافة اسم عربي ووصف مفهوم للأدوار والصلاحيات، مع الإبقاء على permission key ثابتًا للبرمجة.
- منع حذف آخر Admin أو تعطيل وصوله، وحماية أدوار النظام.

اختبارات القبول:
- Admin يستطيع كل العمليات.
- مستخدم محدود ينجح فقط في صلاحياته ويحصل على 403 في غيرها.
- لا تظهر الحقول الحساسة في سجل التدقيق.
- تعمل جميع فلاتر السجل وpagination.

المرحلة 5: استكمال الإدارة الأساسية

راجع وأكمل Backend CRUD لـ:
- العملاء، الموردين، المنتجات، التصنيفات، المستخدمين، الأدوار، والإعدادات.
- البحث والفلاتر والترتيب وpagination وper_page بحدود آمنة.
- validation والقيود الفريدة والعلاقات ومنع الحذف عندما توجد مراجع تشغيلية.
- تفاصيل العميل: الرصيد، كشف الحساب، الدفعات، والفواتير.
- تفاصيل المورد: الرصيد، كشف الحساب، الدفعات، أوامر الشراء والاستلامات.
- ربط منتجات المورد وتكلفة الشراء وSKU المورد والمورد المفضّل إذا كانت ضمن نموذج المشروع.
- توحيد شكل JSON Resources ورسائل أخطاء قواعد العمل.
- Audit logs لكل mutation.

معيار الإنجاز:
- لا يبقى زر أو شاشة إدارية في الواجهة يعتمد على endpoint ناقص أو سلوك وهمي.

المرحلة 6: البيانات المرجعية

أنشئ أو أكمل APIs إدارية لـ:
- المستودعات.
- الوحدات.
- الضرائب.
- الصناديق/Registers.
- طرق الدفع.

لكل نوع:
- index/show/store/update، وdelete فقط إن كان آمنًا؛ وإلا استخدم is_active للتعطيل.
- validation وpagination والبحث.
- منع حذف سجل مستخدم في معاملات سابقة.
- صلاحيات دقيقة وAudit logs.
- endpoints مرجعية خفيفة للاختيارات النشطة في الواجهة عند الحاجة.
- اختبارات CRUD والتعطيل والقيود المرجعية.

المرحلة 7: الفلاتر المحفوظة

المطلوب:
- إكمال SavedFilter كميزة فعلية للمستخدم الحالي.
- API لإنشاء وعرض وتعديل وحذف الفلاتر المحفوظة.
- ربط الفلتر بمورد/صفحة مسموحة، واسم، وشروط JSON validated، وترتيب اختياري، وفلتر افتراضي واحد لكل مستخدم ومورد.
- منع المستخدم من قراءة أو تعديل فلاتر مستخدم آخر.
- قائمة مسموحة للحقول والعمليات لكل مورد لمنع حقن أسماء أعمدة أو queries غير آمنة.
- تطبيق الفلاتر فعليًا على القوائم والتقارير المطلوبة، لا مجرد تخزينها.
- اختبارات الملكية، validation، التطبيق، والحذف.

المرحلة 8: استيراد Excel/CSV وGemini

نفّذ الاستيراد على طبقتين:

أولًا — الاستيراد الحتمي الأساسي:
- دعم CSV وXLSX حقيقيين للمنتجات على الأقل، ثم العملاء والموردين إذا كان النموذج مناسبًا.
- رفع آمن مع حدود للحجم والامتداد وMIME.
- قراءة header mapping، validation لكل صف، واكتشاف التكرار حسب SKU/barcode/email وفق المورد.
- شاشة/endpoint preview يعرض الصفوف الصحيحة والأخطاء والتحذيرات قبل الحفظ.
- لا تُدخل أي صف قبل تأكيد المستخدم.
- دعم all-or-nothing أو partial import كخيار صريح مع تقرير نتيجة واضح.
- تنفيذ الملفات الكبيرة عبر Queue Job مع progress/status وإمكانية فشل قابلة للتشخيص.
- منع تشغيل الملف نفسه مرتين بلا قصد، وتسجيل المستخدم والملف والنتائج دون حفظ أسرار.
- توفير نموذج XLSX قابل للتنزيل بأسماء الأعمدة المطلوبة.

ثانيًا — Gemini للمطابقة والتنظيف:
- أنشئ abstraction/provider داخل Backend حتى لا يرتبط منطق الاستيراد مباشرة بمزوّد واحد.
- نفّذ Gemini provider باستخدام Laravel HTTP client أو SDK متوافق عند الضرورة فقط.
- اقرأ الإعدادات من config/services.php ومتغيرات البيئة، مثل GEMINI_API_KEY وGEMINI_MODEL؛ أضف placeholders فقط إلى .env.example ولا تكتب المفتاح الحقيقي في Git أو قاعدة البيانات أو Frontend.
- جميع اتصالات Gemini تتم من Laravel Backend فقط، ولا يُكشف المفتاح داخل Angular.
- استخدم Gemini لاقتراح مطابقة أسماء الأعمدة، توحيد الأسماء والوحدات والتصنيفات، واكتشاف القيم المشكوك بها؛ لا تسمح له بكتابة البيانات مباشرة.
- اطلب مخرجات JSON منظمة ومحددة schema، ثم تحقق منها محليًا ولا تثق بالمخرجات دون validation.
- اعرض اقتراحات AI في preview ويجب أن يؤكدها المستخدم قبل الحفظ.
- لا ترسل كلمات مرور أو tokens أو بيانات مالية/شخصية غير لازمة. قلّل البيانات المرسلة قدر الإمكان.
- أضف timeout وretry محدودًا وrate limiting وسجل أخطاء منقحًا وتتبّع تكلفة/استهلاك تقريبي إن توفر.
- إذا لم يوجد GEMINI_API_KEY، يبقى الاستيراد الحتمي يعمل، ويعيد مسار AI رسالة إعداد واضحة بدل الانهيار.
- اختبر Gemini عبر Http::fake أو provider fake؛ لا تجعل الاختبارات تعتمد على اتصال خارجي فعلي.

اختبارات القبول:
- CSV وXLSX صحيحان وخاطئان.
- duplicate handling وpreview ثم confirm.
- partial وatomic modes.
- job status ونتيجة الاستيراد.
- اقتراح Gemini وهمي منظم، JSON تالف، timeout وغياب المفتاح.

المرحلة 9: الجودة والدقة المالية والتكامل المحاسبي

المطلوب:
- مراجعة كل الحسابات المالية واستخدام decimal/bcmath وعدم استخدام float للحسابات الحساسة.
- مراجعة transactions وrow locks وrace conditions وidempotency في البيع والاستلام والدفع والمرتجع والجرد والتحويل.
- ضمان أن customer/supplier balances قيم مخزنة مدعومة بقيود ledger append-only ولا تُعدل خارج الخدمات المخصصة.
- فحص N+1، eager loading، indexes، pagination، وحدود الاستعلامات والتقارير الكبيرة.
- مراجعة authorization وmass assignment ورفع الملفات وتسريب الأسرار وrate limits.
- توحيد الأخطاء التشغيلية ورسائل API دون كشف stack traces في Production.
- مراجعة CORS وSanctum وtoken expiration وconfig caching والqueue/scheduler/logging.
- إصلاح جميع الاختبارات المعطلة لأسباب حقيقية، وعزل قاعدة الاختبار تمامًا عن Demo/local.
- إضافة اختبارات التكامل الكاملة للدورات المالية والتشغيلية.
- تحديد واجهة Accounting Export/Integration واضحة ومحايدة للمزوّد: قيود مبيعات، مشتريات، دفعات، ضرائب، مرتجعات، وأرقام مراجع idempotent. لا تربط النظام ببرنامج محاسبي خارجي محدد قبل تحديده مع المستخدم.

الفحوص المطلوبة خلال العمل وفي النهاية:
- vendor/bin/pint --dirty --format agent بعد تعديل PHP.
- اختبارات المرحلة المحددة أولًا باستخدام php artisan test --compact مع الملف أو filter المناسب.
- php artisan test --compact لكامل Backend بعد استقرار المراحل.
- php artisan route:list --except-vendor ومقارنته بالتوثيق.
- فحص migrations على قاعدة اختبار فارغة، واختبار upgrade migrations دون مسح بيانات المستخدم.
- npm run lint وnpm run build وnpm run build:prod إذا تم تعديل Frontend.
- اختبارات API فعلية للدورات الحرجة على بيئة آمنة، وتنظيف بيانات الاختبار المؤقتة.

تعريف الإنجاز النهائي:
1. اكتملت المراحل 0–9 فعليًا أو وُثّق مانع خارجي محدد لا يمكن تجاوزه بدون مفتاح/قرار من المستخدم.
2. جميع endpoints محمية وموثقة ومختبرة.
3. العمليات المالية والمخزنية transaction-safe وتنتج قيودًا وأرصدة متناسقة.
4. الاستيراد CSV/XLSX يعمل دون AI، وGemini يعمل عند وضع المفتاح مع preview وموافقة المستخدم.
5. لا توجد secrets داخل المستودع أو Frontend.
6. لا توجد تغييرات مدمرة أو رجوع لتعديلات المستخدم.

في نهاية كل جلسة أعطني تقريرًا عربيًا واضحًا يتضمن:
- المرحلة والبنود التي اكتملت.
- الملفات التي تغيرت.
- migrations وendpoints الجديدة.
- الاختبارات التي شُغلت ونتيجتها بالأرقام.
- العمليات التي جُرّبت فعليًا.
- أي مخاطر أو مشاكل متبقية.
- المرحلة التالية التي ستبدأ منها الجلسة القادمة.
- أي إعداد خارجي مطلوب مني، مثل وضع GEMINI_API_KEY، بدون طلب إرسال المفتاح داخل المحادثة.
